# Deferred Work

## Deferred from: code review of 2-4-system-shows-empty-state-when-no-match-found (2026-07-26)

- **Step transitions move focus nowhere and announce nothing** (`app/search/page.tsx`). Each step replaces the whole `<main>`, so the control the user just clicked unmounts and focus resets to document top. With no `aria-live` (2-4 Open Question 2), a screen-reader or keyboard user gets silence and must Tab from the top to find the next control. Affects all four steps of the Search screen equally, not just the Empty State — on the Empty State it is worst, because the outcome is *absence*, so silence is indistinguishable from the request never completing. Should be decided once for every step, matching the story's own reasoning for deferring `aria-live`.
- **A dropped response on the expansion burns the final budget unit and permanently blocks the Empty State** (`app/search/page.tsx:152-157`, `app/actions/expandSearch.ts:96`). `consumeSessionUse` runs before matching and notification, so on flaky mobile data the server completes — donors are texted, `Search` rows written — while the client falls into `catch` and shows the retryable "Something went wrong" message. `UNEXPECTED` is not in `isSessionTerminal`, so the button stays enabled and invites exactly the retry the copy asks for; the second click returns `SESSION_EXHAUSTED`. The searcher never sees their matches or the Empty State, while notified donors expect a call from someone who was never shown their number. Story 2.3 slice; fixing it means either an idempotency key per `jti` or consuming budget only after a successful response.
- **Refresh or back/forward escapes the terminal Empty State into a fully-enabled search form** (`app/search/page.tsx:73`). `step` lives in component state while `sessionToken`/`name` live in the query string, so any remount — pull-to-refresh, back from `/search/verify`, iOS discarding a backgrounded tab — returns the user to `"form"` with an enabled Search button on a spent token. They re-pick, submit, burn a rate-limit slot, and get `SESSION_EXHAUSTED`. Pre-existing 2.2/2.3 architecture, but 2.4 is the first step whose correctness depends on being terminal. Same root cause as the already-logged "no way back to the form from the expansion prompt" item — both want step in the URL.

## Deferred from: story context for 3-1-donor-starts-a-self-service-session-via-otp (2026-07-26)

- **Session tokens carry no `purpose`/`aud` claim, so a self-service token is accepted by the search actions.** The JWT payload is `{ sub, jti, iat, exp }` (`lib/infra/jwt.ts:15-20`) and both flows sign with the same `JWT_SIGNING_KEY`. `submitSearch.ts:104` assigns `const searcherPhone = verifiedToken.subject;` and writes it into the `Search` row with no format validation (same in `expandSearch.ts`), so a self-service token (whose `sub` is a cuid) buys one free search and writes a cuid into `Search.searcherPhone`, corrupting that row's FR-8 notification payload. Story 3.1's `subject = donorId` choice closes the *opposite* direction (a Searcher token cannot satisfy `findDonorById`), but not this one. Fixing it means adding a claim to `lib/domain/session.ts` + `lib/infra/jwt.ts` and re-verifying Story 2.1's `done` code — deliberately out of scope for 3.1.
- **Resend OTP link misses the ≥44px tap-target floor on both existing OTP screens** (`app/register/verify/page.tsx:126-132`, `app/search/verify/page.tsx:222-228`). Both render a bare 14px text button, violating UX-DR8/NFR-8. Story 3.1 meets the floor on its new screen; backfilling Epic 1/2's two copies is a separate accessibility pass so the fix lands as one reviewable change.
- **`Button`'s default `loadingText` is `"Sending…"`, but `EXPERIENCE.md:76` specifies `"Sending code…"` for OTP triggers.** Neither existing OTP screen overrides the default (`Button.tsx:12`). Story 3.1 matches the existing precedent rather than the spec, since a third screen differing from the other two is worse for users than a uniform doc mismatch. Change all three together, or amend the spec.
- **The resend link is not replaced by the rate-limit message when the limit is hit**, as `EXPERIENCE.md:68` requires — existing screens render the message in a separate `role="alert"` block and leave the link live. Applies to all OTP screens.
- **`RESEND_COUNTDOWN_SECONDS = 45` and the full countdown block are duplicated verbatim per OTP screen**; Story 3.1 makes a third copy. UX-DR2 (`epics.md:85`) lists "Resend OTP link" as a required *reusable* component. Extraction was not done in 3.1 because no prior story extracted it and doing so would be unrequested scope in a story that already touches Home.
- **The countdown renders a hardcoded `0:` prefix** (`app/register/verify/page.tsx:131`), correct only below 60 seconds. Latent if the countdown is ever tuned upward.

## Deferred from: code review of 2-3-system-suggests-nearby-area-expansion-on-no-match (2026-07-26)

- **SM-3 is not computable from the `Search` table at any row granularity.** `Search` has `id, searcherName, searcherPhone, bloodType, area, createdAt` — no match count, no result flag, no correlation id linking an expansion's rows to the origin search (`prisma/schema.prisma:53-60`). `expandSearch` writes one row per area searched, which records the real extent of an expansion but inflates any naive Search-row count for expansion journeys, biasing SM-3 downward if measured that way. Making SM-3 genuinely measurable needs a `correlationId` (and probably a match-count column) plus a migration — a PM/metrics-design decision, not a code fix. Decided 2026-07-26: keep the fan-out, correct the misleading comment, defer the schema question.
- Rate-limit responses discard the `retryAfterSeconds` the limiter already computed, telling the user only "try again shortly" (`app/actions/expandSearch.ts:52-65`). Inherited verbatim from `submitSearch.ts:48-55`; PRD Open Question 3 leaves thresholds open and EXPERIENCE.md explicitly declines to promise an unenforceable retry time. Applies to every rate-limited action, not just this one.
- No in-page affordance to return to the search form from the expansion prompt (`app/search/page.tsx:166-193`). A searcher who picked the wrong blood type or area can only move forward, spending their last budget unit on the wrong criteria. Pre-existing consequence of the Story 2.2 screen keeping step in component state rather than the URL; fixing it is a change to that screen's shape, not to this story's feature.

## Deferred from: code review of 2-1-searcher-verifies-identity-via-otp (2026-07-11)

- Rate limiting is IP-only, not phone-based — a distributed-IP SMS-bomb against one victim phone isn't blocked (`app/actions/requestSearcherOtp.ts:47-65`). Pre-existing AD-3 design from Story 1.2; PRD §4.6 explicitly scopes IP-only rate limiting for MVP and flags phone-based throttling as a post-launch revisit.
- `ipAddress()` "unknown" fallback collapses all IP-less clients into one shared rate-limit bucket (`app/actions/requestSearcherOtp.ts:47`). Identical pattern present in `registerDonor.ts`/`requestDonorOtp.ts` since Stories 1.1/1.3.
- No rate-limiting or lockout on `verifySearcherOtp` itself — the 6-digit code is brute-forceable via repeated verify calls, even though `OtpChallenge.attempts` is tracked (`app/actions/verifySearcherOtp.ts`; `lib/domain/otp.ts`). Identical gap in `verifyDonorOtp.ts` since Story 1.3; no lockout enforcement exists anywhere in the shared `otp` service yet.
- Server Actions calling out to Redis/Twilio (`requestSearcherOtp`, and pre-existing `requestDonorOtp`/`registerDonor`) have no try/catch around those calls — an outage surfaces as an unstyled framework error rather than a graceful message (`app/actions/requestSearcherOtp.ts:56-65`). Identical pattern since Stories 1.1/1.3.
- `sessionStore.consume`'s get-then-decr has a small non-atomic race window (TTL could expire between the two calls) (`lib/infra/sessionStore.ts:8-16`). Already explicitly accepted as an MVP trade-off in Story 2.1's own Dev Notes ("acceptable here — single-user, budget-of-2 flows, not a high-concurrency resource").
